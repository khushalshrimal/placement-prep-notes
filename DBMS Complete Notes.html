1. What is DBMS? DBMS vs File System
ENGLISH
A database is an organised collection of data. A DBMS (Database Management System) is software that helps us store, retrieve, update and delete that data safely. Examples: MySQL, PostgreSQL, Oracle, MongoDB.
  • File system problems: same data repeated in many files (redundancy), different copies disagree (inconsistency), no security, hard to search, no crash recovery.
  • DBMS advantages: less redundancy, data integrity, security (user permissions), many users at the same time, backup and recovery, easy querying with SQL.
HINGLISH
Database matlab data ka organised collection. DBMS wo software hai jo data ko store, dhoondhne, update aur delete karne me help karta hai, bhi safely. Jaise MySQL, PostgreSQL, Oracle, MongoDB.
  • File system ki problems: same data kai files me repeat hota hai (redundancy), copies alag-alag ho jaati hain (inconsistency), security nahi, search mushkil, crash ke baad recovery nahi.
  • DBMS ke fayde: repetition kam, data sahi rehta hai (integrity), security (permissions), ek saath kai users, backup/recovery, SQL se easy query.
Example: College keeps student data in Excel files per department. Amit’s phone number changes in one file only, so other files are outdated. In a DBMS the number is stored once and every department sees the same value.  (Hinglish: Excel me ek jagah number badla, baaki jagah purana raha. DBMS me data ek baar store hota hai, sab ko wahi dikhta hai.)
Interview line: “DBMS reduces redundancy, maintains integrity, and supports concurrent access with security.”
2. DBMS Components, Users & Architectures
ENGLISH
  • Query processor: DDL interpreter, DML compiler, query optimizer, execution engine.
  • Storage manager: buffer manager, file manager, transaction manager, authorization manager.
  • Data dictionary (catalog): metadata, i.e. data about data (table names, columns, indexes).
  • Users: DBA (controls everything), database designers, application programmers, end users (naive = use apps, casual = run queries, sophisticated = analysts).
  • Architectures: 1-tier (DB on same machine), 2-tier (client ↔ DB), 3-tier (client ↔ app server ↔ DB; most web apps).
  • Languages: DDL, DML (procedural = say how; declarative like SQL = say what), DCL, TCL.
HINGLISH
  • Query processor: DDL interpreter, DML compiler, query optimizer, execution engine.
  • Storage manager: buffer manager, file manager, transaction manager, authorization manager.
  • Data dictionary (catalog): metadata, matlab data ke baare me data (table ke naam, columns, indexes).
  • Users: DBA (sab control karta hai), designers, application programmers, end users (naive = app use karte hain, casual = queries chalate hain, sophisticated = analysts).
  • Architectures: 1-tier (DB usi machine par), 2-tier (client ↔ DB), 3-tier (client ↔ app server ↔ DB; zyadatar web apps).
  • Languages: DDL, DML (procedural = kaise karna hai batao; declarative jaise SQL = kya chahiye batao), DCL, TCL.
3. Data Models, Schema & 3-Level Architecture
ENGLISH
Schema = the design/structure of the database (table names, columns, types). Instance = the actual data at a particular moment. Three levels of abstraction hide complexity:
  • Physical level: how data is stored on disk.
  • Logical level: what data is stored and the relations between them (tables).
  • View level: what each user sees (for example, a teacher sees marks but not salaries).
Data independence: change at a lower level without breaking the level above.
HINGLISH
Schema = database ka design (table ke naam, columns, types). Instance = us waqt ka asli data. Teen levels complexity chhupate hain:
  • Physical level: data disk par kaise store hai.
  • Logical level: kaunsa data hai aur unke beech relations (tables).
  • View level: har user ko kya dikhta hai (teacher ko marks dikhte hain, salary nahi).
Data independence: neeche ke level me change karo to upar wala level na toote.
4. Relational Model & Integrity Constraints
ENGLISH
Terms: relation = table, tuple = row, attribute = column, domain = allowed values of a column, degree = number of columns, cardinality = number of rows. Properties: no duplicate tuples, row/column order does not matter, values are atomic.
  • Domain constraint: value must match the column type/range (age > 0).
  • Entity integrity: primary key can never be NULL.
  • Referential integrity: a foreign key must match an existing primary key (or be NULL).
  • Key constraint: no two rows share the same key value.
Foreign key actions: ON DELETE CASCADE (delete child rows too), SET NULL, RESTRICT/NO ACTION (block the delete). Codd’s rules: 12 rules (0 to 12) that a true relational DBMS should follow, e.g. information rule, guaranteed access, NULL support.
HINGLISH
Terms: relation = table, tuple = row, attribute = column, domain = column ki allowed values, degree = columns ki ginti, cardinality = rows ki ginti. Properties: duplicate tuples nahi, row/column ka order matter nahi karta, values atomic hoti hain.
  • Domain constraint: value column ke type/range ke hisaab se ho (age > 0).
  • Entity integrity: primary key kabhi NULL nahi hoti.
  • Referential integrity: foreign key ki value kisi existing primary key se match kare (ya NULL ho).
  • Key constraint: do rows ki key value same nahi ho sakti.
Foreign key actions: ON DELETE CASCADE (child rows bhi delete), SET NULL, RESTRICT/NO ACTION (delete rok do). Codd’s rules: 12 rules jo ek sachche relational DBMS ko follow karne chahiye (jaise information rule, guaranteed access, NULL support).
5. Keys
ENGLISH
A key identifies rows uniquely or links tables.
  • Super key: any set of columns that is unique per row, e.g. {roll_no}, {roll_no, name}.
  • Candidate key: a minimal super key (no extra column). {roll_no} is one; {roll_no, name} is not, because name is extra.
  • Primary key: the candidate key we choose. Unique + NOT NULL, only one per table.
  • Alternate key: candidate keys not chosen as primary.
  • Foreign key: a column that refers to the primary key of another table. Student.course_id refers to Course.course_id. It can be NULL (Karan has no course) and can repeat.
  • Composite key: a key made of 2+ columns, e.g. (student_id, course_id) in an enrolment table.
HINGLISH
Key rows ko unique pehchanti hai ya tables ko jodti hai.
  • Super key: columns ka koi bhi set jo har row ke liye unique ho, jaise {roll_no}, {roll_no, name}.
  • Candidate key: minimal super key (koi extra column nahi). {roll_no} candidate hai; {roll_no, name} nahi, kyunki name extra hai.
  • Primary key: jo candidate key hum choose karte hain. Unique + NOT NULL, table me sirf ek.
  • Alternate key: wo candidate keys jo primary nahi bani.
  • Foreign key: wo column jo dusri table ki primary key ko refer karta hai. Student.course_id, Course.course_id ko refer karta hai. NULL ho sakta hai (Karan ka course nahi) aur repeat bhi ho sakta hai.
  • Composite key: 2 ya zyada columns se bani key, jaise enrolment table me (student_id, course_id).
Trap: Primary key can never be NULL; a foreign key can. Unique key allows NULL (most DBs allow one), and a table can have many unique keys.
6. ER Model & Relationships
ENGLISH
The ER model is a diagram-based design made before building tables. Entity = real-world thing (Student). Attribute = property (name, age). Relationship = link (Student enrols in Course).
  • One-to-One: Person ↔ Passport. Put a unique foreign key on either side.
  • One-to-Many: one Department has many Teachers. Put the foreign key on the “many” side.
  • Many-to-Many: Students ↔ Courses. Needs a third junction table Enrolment(student_id, course_id).
Weak entity: cannot be identified by its own attributes alone; depends on an owner entity (e.g. a Dependent of an Employee). Attribute types: simple, composite (address = city + pin), multivalued (phone numbers), derived (age from date of birth).
HINGLISH
ER model tables banane se pehle ka diagram-based design hai. Entity = asli cheez (Student). Attribute = property (name, age). Relationship = link (Student Course me enroll karta hai).
  • One-to-One: Person ↔ Passport. Kisi ek side par unique foreign key lagao.
  • One-to-Many: ek Department me kai Teachers. Foreign key “many” wali side par lagti hai.
  • Many-to-Many: Students ↔ Courses. Teesri junction table chahiye: Enrolment(student_id, course_id).
Weak entity: apne attributes se akeli pehchani nahi ja sakti, owner entity par depend karti hai (jaise Employee ka Dependent). Attribute types: simple, composite (address = city + pin), multivalued (kai phone numbers), derived (date of birth se age).
7. EER Model: Generalization, Specialization, Aggregation
ENGLISH
  • Specialization (top-down): split an entity into sub-types. Employee → Manager, Engineer.
  • Generalization (bottom-up): merge similar entities. Car, Bike → Vehicle.
  • Inheritance: sub-entities inherit attributes of the super-entity (“IS-A”).
  • Constraints: disjoint (belongs to only one sub-type) vs overlapping; total (every super-entity must be in a sub-type) vs partial.
  • Aggregation: treat a relationship as an entity so it can join another relationship.
  • Participation: total (every entity must take part) vs partial. Cardinality ratio: 1:1, 1:N, M:N.
ER → tables: entity → table; 1:N → FK on N side; M:N → new junction table; multivalued attribute → separate table; weak entity → table with owner’s key + partial key.
HINGLISH
  • Specialization (top-down): ek entity ko sub-types me todna. Employee → Manager, Engineer.
  • Generalization (bottom-up): milti-julti entities ko jodna. Car, Bike → Vehicle.
  • Inheritance: sub-entities super-entity ke attributes inherit karti hain (“IS-A”).
  • Constraints: disjoint (sirf ek sub-type me) vs overlapping; total (har super-entity kisi sub-type me aaye) vs partial.
  • Aggregation: relationship ko entity ki tarah treat karna, taaki wo dusri relationship me aa sake.
  • Participation: total (har entity part le) vs partial. Cardinality ratio: 1:1, 1:N, M:N.
ER → tables: entity → table; 1:N → N side par FK; M:N → nayi junction table; multivalued attribute → alag table; weak entity → owner ki key + partial key wali table.

9. SQL: Command Types & Common Queries
ENGLISH
DDL (CREATE, ALTER, DROP, TRUNCATE) defines structure. DML (INSERT, UPDATE, DELETE) changes data. DQL (SELECT) reads data. DCL (GRANT, REVOKE) controls permissions. TCL (COMMIT, ROLLBACK, SAVEPOINT) controls transactions.
  • WHERE filters rows before grouping; HAVING filters groups after GROUP BY.
  • DELETE removes chosen rows (can rollback); TRUNCATE removes all rows fast; DROP removes the whole table.
  • Aggregate functions: COUNT, SUM, AVG, MIN, MAX. COUNT(*) counts all rows; COUNT(col) ignores NULLs.
HINGLISH
DDL (CREATE, ALTER, DROP, TRUNCATE) structure banata hai. DML (INSERT, UPDATE, DELETE) data badalta hai. DQL (SELECT) data padhta hai. DCL (GRANT, REVOKE) permissions deta hai. TCL (COMMIT, ROLLBACK, SAVEPOINT) transactions control karta hai.
  • WHERE grouping se pehle rows filter karta hai; HAVING GROUP BY ke baad groups filter karta hai.
  • DELETE chuni hui rows hatata hai (rollback ho sakta hai); TRUNCATE saari rows jaldi hata deta hai; DROP poori table hata deta hai.
  • Aggregate functions: COUNT, SUM, AVG, MIN, MAX. COUNT(*) saari rows ginta hai; COUNT(col) NULL ko ignore karta hai.
Examples (on our Student table): 
-- students per city, only cities with more than 1 student
SELECT city, COUNT(*) AS total
FROM Student
GROUP BY city
HAVING COUNT(*) > 1;           -- Jaipur | 2

-- 2nd highest salary (very common question)
SELECT MAX(salary) FROM Emp
WHERE salary < (SELECT MAX(salary) FROM Emp);

-- find duplicate emails
SELECT email, COUNT(*) FROM Student GROUP BY email HAVING COUNT(*) > 1;
10. Joins & Subqueries
ENGLISH
A join combines rows of two tables using a matching column.
JoinMeaningResult on our data
INNERonly matching rowsAmit-DBMS, Riya-OS
LEFTall left rows + matchesAmit-DBMS, Riya-OS, Karan-NULL
RIGHTall right rows + matchesAmit-DBMS, Riya-OS, NULL-CN
FULLall rows from bothall 4 rows above combined
SELECT s.name, c.title
FROM Student s LEFT JOIN Course c ON s.course_id = c.course_id;
Self join: a table joined with itself (employee → manager). Cross join: every row with every row (3 × 3 = 9 rows). Subquery: a query inside another query. Correlated subquery runs once per outer row, so it is slower.
HINGLISH
Join do tables ki rows ko ek matching column se jodta hai. INNER = sirf matching rows. LEFT = left ki saari rows + right ki matching (na mile to NULL), isliye Karan NULL course ke saath aata hai. RIGHT = right ki saari rows + left ki matching (CN course ka koi student nahi). FULL = dono taraf ki saari rows. Self join: table apne aap se join (employee → manager). Cross join: har row ka har row se combination (3 × 3 = 9). Subquery: query ke andar query. Correlated subquery har outer row ke liye chalti hai, isliye slow hoti hai.
Common Q: Which students have no course? SELECT name FROM Student WHERE course_id IS NULL; (use IS NULL, never = NULL).
11. Advanced SQL: Set Ops, Window Functions, CTE, Constraints
ENGLISH
  • Set operations: UNION (removes duplicates), UNION ALL (keeps them), INTERSECT, EXCEPT/MINUS.
  • Filters: LIKE ‘A%’ (% = any text, _ = one char), IN, BETWEEN, EXISTS, IS NULL. ORDER BY, LIMIT. COALESCE(x,0) replaces NULL. CASE WHEN is SQL’s if-else.
  • Window functions calculate over a group of rows without collapsing them: ROW_NUMBER (1,2,3), RANK (1,1,3), DENSE_RANK (1,1,2).
  • CTE (WITH) is a named temporary result for readable queries. Cursor: processes rows one by one. Constraints: NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK, DEFAULT. ALTER: ADD / MODIFY / DROP COLUMN.
-- Nth highest salary (N=3)
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) r FROM Emp) t
WHERE r = 3;
-- top earner per department
SELECT * FROM (SELECT *, RANK() OVER (PARTITION BY dept ORDER BY salary DESC) r FROM Emp) t WHERE r = 1;
-- delete duplicate rows (keep lowest id)
DELETE FROM Student WHERE id NOT IN (SELECT MIN(id) FROM Student GROUP BY email);
HINGLISH
  • Set operations: UNION (duplicates hatata hai), UNION ALL (rakhta hai), INTERSECT, EXCEPT/MINUS.
  • Filters: LIKE ‘A%’ (% = koi bhi text, _ = ek character), IN, BETWEEN, EXISTS, IS NULL. COALESCE(x,0) NULL ko replace karta hai. CASE WHEN SQL ka if-else hai.
  • Window functions rows ke group par calculate karte hain bina rows ko collapse kiye: ROW_NUMBER (1,2,3), RANK (1,1,3), DENSE_RANK (1,1,2).
  • CTE (WITH) naam wala temporary result hai jo query readable banata hai. Cursor: rows ko ek-ek karke process karta hai. ALTER: column ADD / MODIFY / DROP.
Upar ke queries me: Nth highest salary, department ka top earner, aur duplicate rows delete karna (interview me bahut aate hain).
12. Functional Dependencies & Attribute Closure
ENGLISH
FD A → B: if two rows have the same A they must have the same B (roll_no → name). Trivial FD: B is part of A. Prime attribute = part of some candidate key.
  • Armstrong’s axioms: Reflexivity (if B ⊆ A then A → B), Augmentation (A → B ⇒ AC → BC), Transitivity (A → B, B → C ⇒ A → C). Derived: union, decomposition, pseudo-transitivity.
  • Closure X+: all attributes you can reach from X using the FDs. If X+ = all attributes, X is a super key.
  • Canonical (minimal) cover: simplest equivalent FD set (single attribute on right, no extra left attributes, no redundant FD).
Example: R(A,B,C,D), FDs: A→B, B→C, C→D. A+ = {A,B,C,D} = all, and no smaller set works, so A is the candidate key.
HINGLISH
FD A → B: agar do rows me A same hai to B bhi same hona chahiye (roll_no → name). Trivial FD: B, A ka hi hissa ho. Prime attribute = kisi candidate key ka hissa.
  • Armstrong’s axioms: Reflexivity (B ⊆ A to A → B), Augmentation (A → B ⇒ AC → BC), Transitivity (A → B, B → C ⇒ A → C). Derived: union, decomposition, pseudo-transitivity.
  • Closure X+: X se FDs use karke jitne attributes mil sakte hain. Agar X+ = saare attributes, to X super key hai.
  • Canonical (minimal) cover: sabse simple equivalent FD set (right side me ek attribute, left me extra nahi, koi redundant FD nahi).
Example: R(A,B,C,D), FDs: A→B, B→C, C→D. A+ = {A,B,C,D} = sab, aur chhota set kaam nahi karta, isliye A candidate key hai.
13. Normalization
ENGLISH
Normalization means splitting a big table into smaller related tables to remove redundancy and anomalies. Anomalies: insert (cannot add a course until a student joins), update (change a value in many rows, miss one), delete (deleting the last student also deletes the course info). A functional dependency A → B means: if you know A, you can find exactly one B (roll_no → name).
  • 1NF: every cell holds one value. No lists, no repeating columns.
  • 2NF: 1NF + no partial dependency: a non-key column must depend on the whole composite key.
  • 3NF: 2NF + no transitive dependency: non-key must not depend on another non-key (roll_no → course_id → course_title).
  • BCNF: for every dependency A → B, A must be a super key.
Example (1NF): Row: (1, Amit, “DBMS, OS”) has two values in one cell → split into two rows (1, Amit, DBMS) and (1, Amit, OS).
Example (3NF): Student(roll_no, name, course_id, course_title). Here course_id → course_title, which is transitive. Fix: Student(roll_no, name, course_id) and Course(course_id, course_title).
HINGLISH
Normalization matlab badi table ko chhoti related tables me todna, taaki repetition aur anomalies hat jayein. Anomalies: insert (jab tak student join na kare course add nahi ho sakta), update (value kai rows me badalni hai, ek miss ho gayi), delete (aakhri student hataya to course ki info bhi gayi). Functional dependency A → B ka matlab: A pata ho to B exactly ek milega (roll_no → name).
  • 1NF: har cell me sirf ek value. List nahi, repeating columns nahi.
  • 2NF: 1NF + partial dependency nahi: non-key column poori composite key par depend kare, uske hisse par nahi.
  • 3NF: 2NF + transitive dependency nahi: non-key column kisi dusre non-key par depend na kare (roll_no → course_id → course_title).
  • BCNF: har dependency A → B me A super key hona chahiye.
Example (1NF): (1, Amit, “DBMS, OS”) me ek cell me do values hain, to do rows banao. Example (3NF): course_id → course_title transitive hai, isliye Student aur Course alag tables me karo.
Memory trick: “The key, the whole key, and nothing but the key.” Trade-off: more normalization = less duplication but more joins. Reporting systems sometimes denormalize for speed.
14. Decomposition, 4NF, 5NF & Denormalization
ENGLISH
  • Lossless join decomposition: splitting R into R1, R2 must let you rebuild R exactly. It is lossless if R1 ∩ R2 is a key of R1 or R2.
  • Dependency preserving: every original FD can still be checked in the smaller tables. 3NF can always be both lossless and dependency preserving; BCNF is always lossless but may lose a dependency.
  • MVD (multivalued dependency) A →→ B: for one A there is an independent set of B values. Example: Student(name, hobby, language): hobbies and languages are independent, so they repeat in every combination.
  • 4NF: BCNF + no non-trivial MVD (split into (name, hobby) and (name, language)). 5NF: no join dependency that is not implied by keys.
  • Denormalization: deliberately adding redundancy for faster reads (reports, data warehouses).
HINGLISH
  • Lossless join decomposition: R ko R1, R2 me todne ke baad R wapas bilkul waisa hi banna chahiye. Agar R1 ∩ R2, R1 ya R2 ki key ho to lossless hai.
  • Dependency preserving: original FDs chhoti tables me bhi check ho sakein. 3NF hamesha lossless aur dependency preserving ho sakta hai; BCNF hamesha lossless hai par kabhi dependency kho sakta hai.
  • MVD A →→ B: ek A ke liye B values ka independent set. Example: Student(name, hobby, language): hobbies aur languages independent hain, isliye har combination me repeat hoti hain.
  • 4NF: BCNF + koi non-trivial MVD nahi ((name, hobby) aur (name, language) me todo). 5NF: aisi join dependency nahi jo keys se imply na ho.
  • Denormalization: jaan-boojhkar redundancy daalna taaki read fast ho (reports, data warehouse).
15. Transactions & ACID
ENGLISH
A transaction is a group of operations treated as one logical unit. Example: transfer ₹500 from A to B = (1) debit A, (2) credit B. If step 2 fails, step 1 must be undone.
  • Atomicity: all or nothing (done by rollback/undo log).
  • Consistency: database goes from one valid state to another; rules and constraints hold (total money stays same).
  • Isolation: parallel transactions do not disturb each other.
  • Durability: after COMMIT, data survives crashes (done by write-ahead log).
States: Active → Partially Committed → Committed, or Active → Failed → Aborted.
HINGLISH
Transaction kai operations ka group hai jo ek logical unit ki tarah chalta hai. Example: A se B ko ₹500 bhejna = (1) A se debit, (2) B me credit. Agar step 2 fail ho to step 1 undo hona chahiye.
  • Atomicity: ya sab ya kuch nahi (rollback/undo log se).
  • Consistency: database ek valid state se dusri valid state me jata hai; rules na tootein (total paisa same rahe).
  • Isolation: ek saath chalte transactions ek-dusre ko disturb na karein.
  • Durability: COMMIT ke baad data crash me bhi safe rahe (write-ahead log se).
States: Active → Partially Committed → Committed, ya Active → Failed → Aborted.
BEGIN;
UPDATE Account SET balance = balance - 500 WHERE id = 'A';
UPDATE Account SET balance = balance + 500 WHERE id = 'B';
COMMIT;   -- or ROLLBACK; if anything fails
16. Schedules & Serializability
ENGLISH
A schedule is the order in which operations of several transactions run. Serial = one transaction fully after another (always correct). Non-serial = interleaved (fast, but must be equal to some serial order).
  • Conflict: two operations of different transactions on the same item where at least one is a write (R-W, W-R, W-W).
  • Conflict serializable: can be turned into a serial schedule by swapping non-conflicting operations. Test: draw a precedence graph (edge Ti → Tj for each conflict); no cycle = serializable.
  • View serializable: same reads-from and final writes as some serial schedule (a wider class).
  • Recoverable: a transaction commits only after the one it read from commits. Cascadeless (ACA): reads only committed data. Strict: no read or write of an item until its last writer commits. Cascading rollback = one abort forces others to abort.
HINGLISH
Schedule matlab kai transactions ke operations ka chalne ka order. Serial = ek transaction poora, phir dusra (hamesha sahi). Non-serial = interleaved (fast, lekin kisi serial order ke barabar hona chahiye).
  • Conflict: alag transactions ke do operations same item par, jinme kam se kam ek write ho (R-W, W-R, W-W).
  • Conflict serializable: non-conflicting operations swap karke serial schedule ban jaye. Test: precedence graph banao (har conflict par Ti → Tj edge); cycle nahi = serializable.
  • View serializable: kisi serial schedule jaisa reads-from aur final writes (bada class).
  • Recoverable: transaction tab commit kare jab jisse usne padha wo commit ho chuka ho. Cascadeless (ACA): sirf committed data padhe. Strict: item ka last writer commit hone tak na read na write. Cascading rollback = ek abort se baaki bhi abort.
17. Concurrency, Isolation Levels, Locks & Deadlock
ENGLISH
When many users work together these problems can appear:
  • Dirty read: reading another transaction’s uncommitted data (which may be rolled back).
  • Non-repeatable read: same row read twice gives different values, because someone updated it in between.
  • Phantom read: same query run twice returns new extra rows.
  • Lost update: two transactions overwrite each other’s change.
Isolation levels (low to high safety): Read Uncommitted → Read Committed → Repeatable Read → Serializable. Higher level = safer but slower.
Locks: shared (read) lock lets many readers; exclusive (write) lock lets only one writer. 2PL (two-phase locking): a transaction first only acquires locks (growing phase), then only releases them (shrinking phase) which guarantees serializability.
Deadlock: T1 holds lock on X and waits for Y, T2 holds Y and waits for X, so both wait forever. The DBMS detects the cycle (wait-for graph) and aborts one “victim”. Prevent: lock in a fixed order, keep transactions short, use timeouts.
HINGLISH
Jab kai users ek saath kaam karte hain to ye problems aati hain:
  • Dirty read: dusre transaction ka uncommitted data padh lena (wo rollback bhi ho sakta hai).
  • Non-repeatable read: ek hi row do baar padhne par alag value, kyunki beech me kisi ne update kar di.
  • Phantom read: same query dobara chalane par nayi extra rows aa jaana.
  • Lost update: do transactions ek-dusre ka change overwrite kar dein.
Isolation levels (kam se zyada safety): Read Uncommitted → Read Committed → Repeatable Read → Serializable. Level jitna high, safety zyada, speed kam.
Locks: shared (read) lock me kai readers chalte hain; exclusive (write) lock me sirf ek writer. 2PL: pehle sirf locks lo (growing phase), phir sirf chhodo (shrinking phase); isse serializability milti hai.
Deadlock: T1 ke paas X ka lock hai aur Y chahiye, T2 ke paas Y hai aur X chahiye, to dono hamesha ke liye atak jaate hain. DBMS cycle detect karke ek “victim” ko abort kar deta hai. Bachav: locks fixed order me lo, transactions chhote rakho, timeout lagao.
18. Concurrency Control Protocols
ENGLISH
  • Lock-based: shared (S) and exclusive (X) locks. 2PL: growing phase (only lock) then shrinking phase (only unlock); guarantees serializability but deadlock is possible. Strict 2PL holds X locks until commit (avoids cascading rollback); Rigorous 2PL holds all locks until commit.
  • Lock granularity: row, page, table, database. Intent locks (IS, IX) at higher levels show that finer locks exist below.
  • Timestamp ordering: each transaction gets a timestamp; older ones win. Each item keeps read-TS and write-TS; a late operation is rolled back. No locks, no deadlock.
  • Optimistic (validation): read → validate → write; good when conflicts are rare.
  • MVCC: keeps multiple versions so readers never block writers (PostgreSQL, Oracle, MySQL InnoDB).
  • Deadlock handling: prevention with wait-die / wound-wait (using timestamps), detection with wait-for graph (cycle = deadlock), timeout. Starvation: a transaction waits forever; fix with fair queues.
HINGLISH
  • Lock-based: shared (S) aur exclusive (X) locks. 2PL: growing phase (sirf lock) phir shrinking phase (sirf unlock); serializability milti hai par deadlock ho sakta hai. Strict 2PL X locks commit tak rakhta hai (cascading rollback nahi); Rigorous 2PL saare locks commit tak.
  • Lock granularity: row, page, table, database. Intent locks (IS, IX) upar ke level par batate hain ki neeche chhote locks hain.
  • Timestamp ordering: har transaction ko timestamp milta hai; purana jeetta hai. Har item ka read-TS aur write-TS hota hai; late operation rollback. Lock nahi, deadlock nahi.
  • Optimistic (validation): read → validate → write; jab conflicts kam hon tab accha.
  • MVCC: kai versions rakhta hai, isliye readers writers ko block nahi karte (PostgreSQL, Oracle, MySQL InnoDB).
  • Deadlock handling: prevention wait-die / wound-wait se (timestamps), detection wait-for graph se (cycle = deadlock), timeout. Starvation: transaction hamesha wait kare; fair queue se fix.
19. Recovery Techniques
ENGLISH
  • Failures: transaction (error, abort), system (crash, power cut; memory lost), media (disk crash).
  • Log: records like <T1 start>, <T1, X, old, new>, <T1 commit>. WAL (write-ahead logging): write the log to disk before the data page.
  • Deferred update: DB changes only after commit (only REDO needed). Immediate update: changes before commit (needs UNDO and REDO).
  • Checkpoint: a saved safe point; recovery starts there. After a crash: REDO committed transactions, UNDO uncommitted ones.
  • Buffer policies: steal (uncommitted pages may reach disk, needs UNDO) / no-steal; force (flush at commit) / no-force (needs REDO). Most DBs use steal + no-force.
  • Shadow paging: keep the old page table; switch to the new one on commit (no log, but copying is costly). ARIES: Analysis → Redo → Undo. Backups handle media failure.
HINGLISH
  • Failures: transaction (error, abort), system (crash, bijli jana; memory chali jati hai), media (disk kharab).
  • Log: <T1 start>, <T1, X, old, new>, <T1 commit> jaise records. WAL: log ko data page se pehle disk par likho.
  • Deferred update: DB commit ke baad hi badalta hai (sirf REDO chahiye). Immediate update: commit se pehle badalta hai (UNDO aur REDO dono).
  • Checkpoint: safe point; recovery wahin se shuru. Crash ke baad: committed ko REDO, uncommitted ko UNDO.
  • Buffer policies: steal (uncommitted pages disk par ja sakte hain, UNDO chahiye) / no-steal; force (commit par flush) / no-force (REDO chahiye). Zyadatar DB steal + no-force use karte hain.
  • Shadow paging: purani page table rakho, commit par nayi par switch; log nahi chahiye par copy mehenga. ARIES: Analysis → Redo → Undo. Backups media failure ke liye.
20. Storage & File Organization
ENGLISH
  • Storage hierarchy (fast & small to slow & big): registers, cache, RAM, SSD/HDD, tape. RAM is volatile; disks are non-volatile.
  • Disk access time = seek time + rotational latency + transfer time. Data moves in blocks, so minimising block reads is the goal.
  • RAID: 0 = striping (speed, no safety), 1 = mirroring, 5 = striping + parity (one disk can fail), 10 = mirror + stripe.
  • File organisation: heap (unordered, fast insert), sequential (sorted), hashed (position from hash of key), clustered (related records together).
  • Records: fixed vs variable length; blocking factor = records per block; spanned vs unspanned records. Buffer manager caches blocks in RAM and uses replacement policies like LRU.
HINGLISH
  • Storage hierarchy (fast & chhota se slow & bada): registers, cache, RAM, SSD/HDD, tape. RAM volatile hai; disk non-volatile.
  • Disk access time = seek time + rotational latency + transfer time. Data blocks me move hota hai, isliye goal hai block reads kam karna.
  • RAID: 0 = striping (speed, safety nahi), 1 = mirroring, 5 = striping + parity (ek disk fail ho sakti hai), 10 = mirror + stripe.
  • File organisation: heap (unordered, insert fast), sequential (sorted), hashed (key ke hash se jagah), clustered (related records saath).
  • Records: fixed vs variable length; blocking factor = ek block me records; spanned vs unspanned. Buffer manager blocks ko RAM me cache karta hai aur LRU jaisi replacement policy use karta hai.
21. Indexing, Views, Procedures & Triggers
ENGLISH
Index: like the index of a book; it finds rows fast without scanning the whole table. Without an index a search checks every row (O(n)); a B-tree index finds it in O(log n).
  • Clustered: decides the physical order of rows; only one per table (usually the primary key).
  • Non-clustered: separate structure with pointers to rows; many allowed.
  • Cost: reads get faster, but INSERT/UPDATE get slower and extra space is used. Index columns that are often in WHERE, JOIN or ORDER BY.
CREATE INDEX idx_city ON Student(city);
View: a saved SELECT that acts like a virtual table (hides columns, simplifies queries). Stored procedure: SQL code saved in the database and reused by name. Trigger: code that runs automatically on INSERT/UPDATE/DELETE (e.g. write to an audit log). Constraints: NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK, DEFAULT.
HINGLISH
Index kitaab ke index jaisa hai; poori table scan kiye bina rows jaldi dhoondhta hai. Index nahi ho to har row check hoti hai (O(n)); B-tree index se O(log n) me mil jata hai.
  • Clustered: rows ka physical order decide karta hai; table me sirf ek (aksar primary key).
  • Non-clustered: alag structure jisme rows ke pointers hote hain; kai ho sakte hain.
  • Cost: read fast, lekin INSERT/UPDATE slow aur extra space. Wo columns index karo jo WHERE, JOIN ya ORDER BY me aksar aate hain.
View: saved SELECT jo virtual table ki tarah kaam karta hai (columns chhupata hai, query simple banata hai). Stored procedure: database me save SQL code, naam se baar-baar use. Trigger: INSERT/UPDATE/DELETE par apne aap chalne wala code (jaise audit log me entry). Constraints: NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK, DEFAULT.
22. Indexing Deep Dive: B-Tree, B+ Tree & Hashing
ENGLISH
  • Index types: primary (on sorted key; can be sparse), clustering, secondary (on non-key; must be dense), multilevel (index of an index). Dense = entry for every record; sparse = entry per block.
  • B-tree: balanced, multi-way tree; keys and data pointers in every node. B+ tree: data pointers only in leaves, and leaves are linked in a list, so range queries (BETWEEN, ORDER BY) are fast. Height is small, so search = O(log n) with few disk reads. Used by most databases.
  • Hashing: bucket = h(key). Perfect for equality search O(1), bad for ranges. Collisions: chaining or open addressing. Dynamic hashing: extendible and linear hashing grow without full rebuild.
  • Others: bitmap index (low-cardinality columns like gender), composite index follows the leftmost prefix rule (index (a,b) helps queries on a, or a and b, not b alone), covering index holds all needed columns.
HINGLISH
  • Index types: primary (sorted key par; sparse ho sakta hai), clustering, secondary (non-key par; dense hona zaroori), multilevel (index ka index). Dense = har record ki entry; sparse = har block ki entry.
  • B-tree: balanced multi-way tree; har node me keys aur data pointers. B+ tree: data pointers sirf leaves me aur leaves linked list me jude hote hain, isliye range queries (BETWEEN, ORDER BY) fast. Height chhoti, to search O(log n) me kam disk reads. Zyadatar databases yahi use karte hain.
  • Hashing: bucket = h(key). Equality search O(1), range ke liye bekaar. Collisions: chaining ya open addressing. Dynamic hashing: extendible aur linear hashing bina poora rebuild kiye badhte hain.
  • Others: bitmap index (kam values wale columns jaise gender), composite index me leftmost prefix rule (index (a,b) a ya a,b par kaam karta hai, akele b par nahi), covering index me query ke saare columns hote hain.
23. Query Processing & Optimization
ENGLISH
Steps: parse (syntax) → validate (tables/columns exist) → convert to relational algebra → optimize → execution plan → execute. The optimizer picks the plan with the lowest estimated cost (mostly disk I/O) using table statistics.
  • Heuristics: push selections down (filter early), project early, do the most selective join first, replace cartesian product + selection with a join.
  • Join algorithms: nested loop (simple, slow), block nested loop, index nested loop (uses an index), sort-merge (sorted inputs), hash join (equality joins, large tables).
  • Pipelining passes rows on immediately; materialization stores temporary results.
  • Tuning tips: use EXPLAIN to see the plan, avoid SELECT *, index WHERE/JOIN columns, do not wrap indexed columns in functions, prefer JOIN over correlated subqueries when possible.
HINGLISH
Steps: parse (syntax) → validate (tables/columns hain ya nahi) → relational algebra me convert → optimize → execution plan → execute. Optimizer table statistics se sabse kam estimated cost (zyadatar disk I/O) wala plan chunta hai.
  • Heuristics: selection pehle lagao (jaldi filter), projection jaldi, sabse selective join pehle, cartesian product + selection ki jagah join.
  • Join algorithms: nested loop (simple, slow), block nested loop, index nested loop (index use), sort-merge (sorted inputs), hash join (equality joins, badi tables).
  • Pipelining rows ko turant aage bhejta hai; materialization temporary results store karta hai.
  • Tuning tips: plan dekhne ke liye EXPLAIN, SELECT * avoid, WHERE/JOIN columns par index, indexed column par function mat lagao, ho sake to correlated subquery ki jagah JOIN.
24. SQL vs NoSQL, CAP & Recovery (Basics)
ENGLISH
SQL (relational): tables, fixed schema, strong ACID, joins; best for banking, ERP. NoSQL: flexible schema, scales horizontally; types: document (MongoDB), key-value (Redis), column (Cassandra), graph (Neo4j); best for huge, fast-changing data like feeds and logs. CAP theorem: a distributed database can fully guarantee only 2 of 3: Consistency, Availability, Partition tolerance. Recovery: the log records every change; after a crash redo committed work and undo uncommitted work. A checkpoint saves a safe point so recovery starts from there, not from the beginning.
HINGLISH
SQL (relational): tables, fixed schema, strong ACID, joins; banking, ERP ke liye best. NoSQL: flexible schema, horizontally scale hota hai; types: document (MongoDB), key-value (Redis), column (Cassandra), graph (Neo4j); feeds aur logs jaise bade, tezi se badalte data ke liye accha. CAP theorem: distributed database me teen me se sirf 2 pakke mil sakte hain: Consistency, Availability, Partition tolerance. Recovery: log har change record karta hai; crash ke baad committed kaam redo aur uncommitted kaam undo hota hai. Checkpoint ek safe point save karta hai, taaki recovery shuru se na karni pade.
25. Distributed DB, Data Warehouse & Security
ENGLISH
  • Distributed DB: data on many sites. Fragmentation: horizontal (rows), vertical (columns). Replication: copies for speed and safety. Sharding = horizontal partitioning across servers. 2-Phase Commit (2PC): coordinator asks all sites to prepare; if all say yes, it sends commit, else abort. See CAP theorem.
  • Data warehouse: read-heavy store for analysis. OLTP (many small transactions, normalized) vs OLAP (few big analytical queries, denormalized). ETL: extract, transform, load. Star schema: central fact table + dimension tables (snowflake = normalized dimensions). OLAP operations: roll-up, drill-down, slice, dice, pivot.
  • Security: authentication (who are you), authorization (GRANT/REVOKE, roles), views to hide columns, encryption, auditing, backups. SQL injection: attacker puts SQL in input; prevent with prepared statements (parameterized queries).
HINGLISH
  • Distributed DB: data kai sites par. Fragmentation: horizontal (rows), vertical (columns). Replication: speed aur safety ke liye copies. Sharding = rows ko kai servers me baantna. 2-Phase Commit (2PC): coordinator sab sites se prepare poochta hai; sab haan bole to commit, warna abort. CAP theorem bhi dekho.
  • Data warehouse: analysis ke liye read-heavy store. OLTP (bahut chhote transactions, normalized) vs OLAP (kam lekin bade analytical queries, denormalized). ETL: extract, transform, load. Star schema: beech me fact table + dimension tables (snowflake = normalized dimensions). OLAP operations: roll-up, drill-down, slice, dice, pivot.
  • Security: authentication (tum kaun ho), authorization (GRANT/REVOKE, roles), columns chhupane ke liye views, encryption, auditing, backups. SQL injection: attacker input me SQL daal deta hai; bachne ke liye prepared statements (parameterized queries).
